otlp/duplicate-index-key/bad-last
    A resource that repeats one index attribute key with two different
    values. Upstream's `streamLabels` is a map, so the LAST write wins
    (pkg/loghttp/push/otlp.go:191-193 @ v3.7.4) and ValidateLabels is
    charged on that value: `[k8s.pod.name="ok", k8s.pod.name=<bx2049>]` is
    400 there. Ours collapses the repeat through
    `LabelSet::from_normalized`, whose resolution is issue #4's frozen
    greatest-(key, value) rule, so the bound is charged on the value that
    would actually be stored -- "ok" -- and the push is accepted. Matching
    upstream's choice would mean validating a value we do not store, which
    is the defect the first round of this issue was about. Pre-existing:
    the same verdict is produced by the previous implementation, which
    validated the same collapsed set. Reversing the two values
    (`bad-first`) agrees on both sides. OTLP's own data model requires
    attribute keys to be unique within a map, so this is undefined input.

otlp/index-key-map-value-long-nested-key
    A MAP-valued index attribute. `attributeToLabels`
    (pkg/loghttp/push/otlp.go:602-640 @ v3.7.4) recurses into a map value
    and emits one label per leaf, named `<parent>_<leaf>`, so a 1025-byte
    nested key becomes a 1038-byte LABEL NAME upstream and trips the
    name-length bound. PulsusDB renders a map attribute to a single
    JSON-valued label (issue #109), so the long key ends up inside a value
    that is under the value bound. This is the attribute-flattening
    difference, not the bound: the same payload with a long nested VALUE
    (`otlp/index-key-map-value-long-nested-value`) is 400 on both sides,
    by different routes. Belongs with issue #109, not here.

json/65537-raw-empty-keys
    65,537 raw JSON keys in one `stream` object, all empty-valued.
    `WithoutEmpty` drops every one of them upstream, leaving the injected
    `service_name` and a 204. PulsusDB refuses at
    MAX_RAW_LABEL_PAIRS_PER_STREAM, a decode-time materialization cap the
    reference does not have -- the JSON transport must retain empty-valued
    pairs until their names have been grammar-checked and the map's
    last-write-wins collapse has happened. Ledger residual 3. The sibling
    cases `json/257-nonempty` and `pb/257-nonempty` are the other direction
    of the same residual: both sides answer 400, ours with the decode cap's
    wording rather than `has 257 label names; limit 15`.
