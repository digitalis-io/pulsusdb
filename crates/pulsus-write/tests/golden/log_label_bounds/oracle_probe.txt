compare.py also needs a Loki source checkout containing revision b318f282
(LOKI_SRC, default /home/hayato/git/loki): the eighteen OTLP index-label
names are READ out of `pkg/loghttp/push/otlp_config.go` at that revision
with `git show`, not transcribed into the harness. A case set generated
over a copied list is still a case set drawn from our own model of the
rule -- which is exactly how a wrong selection rule passed 44/44 in an
earlier round. The script exits non-zero rather than falling back to a copy
if it cannot read the reference.

Success statuses differ by protocol and are treated as equal: Loki answers
204 on /loki/api/v1/push and on /otlp/v1/logs; PulsusDB answers 204 on
/loki/api/v1/push and 200 on /v1/logs (the OTLP spec's success code).

These are statuses, and a status cannot see what was STORED. The four
`otlp/index-key-vs-near-miss/*` cases agree here and diverge in storage:
upstream keeps the near-miss spelling as structured metadata while we index
it, both spellings canonicalize onto one label name, and our collision rule
keeps the near-miss -- so a 2049-byte value lands on a stream label the
bound passed at two bytes. That half is asserted on stored state instead,
by `otlp_logs::tests::an_index_attribute_and_its_near_miss_collide_on_the_unvalidated_value`
and, out of live ClickHouse, by
`loki_push_live::an_otlp_near_miss_spelling_stores_an_over_wide_indexed_label`.

The `json/streams-key-*` group is the second place a status cannot settle
the question, and is why the group exists. Loki matches the envelope's
`streams` field with ASCII case folding, so `Streams`/`STREAMS`/`StReAmS`
are accepted AND stored; before issue #374 both sides answered 204 here
while PulsusDB silently dropped the lines, so status agreement reported
parity over data loss. These cases pin the wire; the storage half is
asserted by
`loki_push_live::a_case_variant_streams_key_is_accepted_and_its_lines_are_stored`
(each spelling's line read back out of ClickHouse) and hermetically by
`loki_push::tests::parse_json_matches_the_streams_key_case_insensitively`.

The `json/superseded-*` group is the third, and it is the same trap one
level on: last-wins means a cap-breaking occurrence the reference has
already discarded must not decide the request. Every row in it was 400 on
this branch and 204 upstream before round 11. The group is the ENUMERATION
of "a cap chargeable before a resolution point" -- the envelope `streams`
key, a stream object's `stream` key and its `values` key, crossed with each
per-occurrence cap reachable inside them -- not the three that were probed.
Storage is asserted by
`loki_push_live::a_superseded_over_cap_value_is_accepted_and_the_final_one_is_stored`
(the final line read back, the superseded stream asserted absent) and
hermetically, in both directions, by
`loki_push::tests::parse_json_a_superseded_over_cap_value_does_not_decide_the_request`.

The `json/drained-*` group is the same trap one level further on, and it is
what round 12 found: deferring a cap left the remainder of an over-cap run to
`serde::de::IgnoredAny`, a bracket-matching skip that checks no types, so
crossing a cap turned the checking OFF. Each row has a `-under-cap` control
carrying the SAME malformed tail one element below the cap, and the control
is what makes the row mean anything -- it was already 400 on both sides while
the over-cap row was 204 here and 400 upstream, which is how "the cap
switches the checking off" is told apart from "the input is bad". A fix that
made a cap unreachable would agree on every over-cap row and fail its
control. Hermetically the same thing is asserted as message EQUALITY across
below-cap / past-cap / past-cap-and-superseded, by
`loki_push::tests::parse_json_a_drained_value_is_checked_exactly_like_a_retained_one`.

The `json/ignored-depth-*` group is the depth half of that, and the ceiling is
the reference's: jsoniter's maxDepth = 10000 (iter.go:331-338 @ v1.1.12).
What that counts is NOT the brackets to the left of the value, which is why
each row carries its own boundary literal and why a single constant would be
wrong in two of the three positions: the envelope object counts
(oneFieldStructDecoder increments, reflect_struct_decoder.go:574-594), the
`streams` ARRAY does not (sliceDecoder never increments,
reflect_slice.go:59-99), and the stream object and everything under it do,
because LogProtoStream has an UnmarshalJSON (pkg/loghttp/query.go:99 @ v3.7.4)
that jsoniter reaches through SkipAndReturnBytes, whose iter.Skip() walks the
object with ReadObjectCB / ReadArrayCB (iter_skip_strict.go:85-99). So the
deepest ACCEPTED nest is 9,999 under an unknown envelope key, 9,998 under an
unknown key inside a stream and 9,996 as an entry's fourth element; each row
is paired with the first level refused, all six bisected against these two
servers rather than read off a constant. `-126` and `-127` are the shallow
end: 127 was PulsusDB's own over-rejection until round 14 (serde_json's fixed
RECURSION_LIMIT of 128), and both are now agreements. The three `-200000`
rows keep the far-past-everything shape in each position, so a ceiling that
went missing on one side could not pass as a ceiling that merely differs.

The `json/ignored-number-*` group is there because depth is not the only thing
upstream's skip still checks. `trySkipNumber` walks a run of digits with at
most one dot and skips it unevaluated, but hands anything else -- an exponent,
in practice -- to `ParseFloat`, which fails on OVERFLOW
(iter_skip_strict.go:10-59, iter_float.go:186-204 @ jsoniter v1.1.12). So an
ignored `1e999` is 400 there and an ignored 400-digit integer is 204. Reading
a discarded value as raw text is what makes the depth rows above agree, and on
its own it would have opened this hole in exchange -- `-int` is the row that
tells the two apart, and `-at-max`/`-past-max` sit either side of `f64::MAX`,
which is where "overflow" is actually decided.

Several cases are large by design: `-streams-stream-count` and
`drained-streams-non-object` carry 1,000,001 stream objects (3 MB),
`drained-values-non-array` 100,001 entries (2.8 MB), and the two
`-shared-budget` cases 30 and 38 streams of 100,000 minimal entries (27 MB
and 34 MB), which Loki materializes before discarding. All sit inside Loki's
100 MiB `distributor.max-recv-msg-size` and PulsusDB's 64 MiB decompressed
body cap, which is what makes the recorded shared-budget divergence reachable
rather than theoretical.

Long runs of one alphanumeric are squashed as <cxN> = N repetitions of c
(100 or more) -- by compare.py's own `trim`, so a fresh run reproduces these
bodies rather than a hand-post-processed copy of them.
Loki's plain-text bodies carry a trailing newline from Go's http.Error,
shown as \n; OTLP bodies are google.rpc.Status protobufs, so the leading
framing byte prints as a replacement character (Loki's carries only the
message field; ours also carries `code = 3`, our OTLP-error convention).

Every recorded body reproduces. Two things upstream puts in one are not a
function of the request -- the order of a multi-failure body's error groups,
and the read-buffer window a jsoniter decode error quotes -- and compare.py's
`trim` sorts the first and elides the second; the reproduce recipe above says
what was measured and why neither can move a verdict. A third, the request
window quoted back in a reject, is handled in the CASES instead: those bodies
carry a fixed timestamp rather than `now` (they are refused at decode, before
a timestamp is looked at, so freshness cannot matter to them), while the rows
upstream accepts keep `now`.

otlp/duplicate-index-key/bad-last
    A resource that repeats one index attribute key with two different
    values. Upstream's `streamLabels` is a map, so the LAST write wins
    (pkg/loghttp/push/otlp.go:191-193 @ v3.7.4) and ValidateLabels is
    charged on that value: `[k8s.pod.name="ok", k8s.pod.name=<bx2049>]` is
    400 there. Ours collapses the repeat through
    `LabelSet::from_normalized`, whose resolution is issue #4's frozen
    greatest-(key, value) rule, so the bound is charged on the value that
    would actually be stored -- "ok" -- and the push is accepted. Matching
    upstream's choice would mean validating a value we do not store, which
    is the defect the first round of this issue was about. Pre-existing:
    the same verdict is produced by the previous implementation, which
    validated the same collapsed set. Reversing the two values
    (`bad-first`) agrees on both sides. OTLP's own data model requires
    attribute keys to be unique within a map, so this is undefined input.

otlp/index-key-map-value-long-nested-key

    (pkg/loghttp/push/otlp.go:602-640 @ v3.7.4) recurses into a map value

    difference, not the bound: the same payload with a long nested VALUE
    (`otlp/index-key-map-value-long-nested-value`) is 400 on both sides,
    by different routes. Belongs with issue #109, not here.
