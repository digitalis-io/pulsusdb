# PulsusDB Features & Compatibility Matrix

This document enumerates every feature PulsusDB commits to and the milestone in which it lands. It is the source of truth for scoping GitHub issues — every row here should trace to one or more issues.

Two product decisions frame the matrix:

1. **The OpenTelemetry Collector is the ingestion path.** Logs, metrics, traces, and profiles arrive via OTLP (metrics alternatively via the collector's Prometheus remote-write exporter). OTLP endpoints are always on and land with each signal's milestone. Foreign push protocols are optional compatibility receivers, off by default.
2. **The PulsusDB API is product-neutral.** Primary query paths live under `/api/{logs,traces,profiles,rules}/v1/...` plus the standard Prometheus HTTP API for metrics. Third-party API surfaces (log/trace/profile datasource protocols) are flag-gated aliases (`PULSUS_COMPAT_ENDPOINTS`) onto the same handlers — see [api.md §8](api.md).

Milestones: **M0** scaffolding · **M1** logs proof · **M2** metrics proof · **M3** downsampling · **M4** traces · **M5** profiles · **M6** full language compliance + compat ingest breadth · **M7** native histograms + operations. See §7.

M1 and M2 are deliberately **narrow proof milestones**: the project exists because reads are slow, so the earliest code must validate the storage and planner design against captured real-world slow queries — full language parity comes in M6, after the read path has earned it with benchmark evidence.

## 1. Ingestion

### 1.1 Primary (always on)

| Protocol | Endpoint | Formats | Milestone |
|----------|----------|---------|-----------|
| OTLP logs | `POST /v1/logs` | protobuf | M1 |
| OTLP metrics | `POST /v1/metrics` | protobuf (exponential histograms flatten to classic `_bucket`/`_sum`/`_count` series until native-histogram storage lands in M7) | M2 |
| OTLP traces | `POST /v1/traces` | protobuf | M4 |
| OTLP profiles | `POST /v1development/profiles` | protobuf (experimental OTLP signal) | M5 |
| Prometheus remote write | `POST /api/v1/write` | snappy protobuf (`prompb.WriteRequest`) — supports the collector's `prometheusremotewrite` exporter | M2 |
| Profile ingest (native) | `POST /api/profiles/v1/ingest` | pprof | M5 |
| OTLP/JSON encoding | all OTLP endpoints | JSON per OTLP/HTTP spec | M6 |

### 1.2 Compatibility receivers (flag-gated, M6)

`POST /loki/api/v1/push` (JSON/protobuf) · Zipkin `POST /tempo/spans`, `/api/v2/spans` · `POST /ingest` (pprof alias, ships M5) · InfluxDB line protocol `POST /influx/api/v2/write` · Datadog `POST /api/v2/logs`, `/api/v2/series` · Elastic `POST /_bulk`, `/{target}/_bulk`, doc endpoints · remote-write path aliases.

### 1.3 Cross-cutting ingest features (M1 onward)

gzip/snappy/zstd request decompression · sync/async insert selection per request (`X-Pulsus-Async`) · per-request database routing (`X-Pulsus-Database`) · bounded buffering with `429` backpressure · per-protocol ingest metrics. Retention is per-table/database configuration; there is deliberately no per-write TTL override in v1.

**LogQL — M1 proof subset:** stream selectors with `=`, `!=`, `=~`, `!~`; line filters `|=`, `!=`, `|~`, `!~`; range aggregations `rate`, `count_over_time`, `bytes_rate`, `bytes_over_time`; vector aggregations `sum`, `avg`, `min`, `max`, `count` with `by`/`without`. This subset is exactly what's needed to prove the read path: index-served stream resolution, skip-index line filters, and rollup-served counts.

**LogQL — parity (M6):** parsers `json`, `logfmt` (with the `--strict`/`--keep-empty` flags — M8-LQ1), `regexp`, `pattern`; the `unpack`, `decolorize`, `drop`, and `keep` pipeline stages (M8-LQ1); label filters (string + numeric with duration/bytes units); `line_format`, `label_format`, `unwrap`; full over-time set (`sum/avg/min/max/stddev/stdvar/quantile/first/last/absent_over_time`); `stddev`, `stdvar`, `topk`, `bottomk` vector aggregations; binary operations between range vectors. Range aggregations read raw and slide (issue #227), giving up the 5s rollup speedup for bit-exact Loki parity; the configurable-resolution rollup remains for instant/other uses. The stream (log) pipeline landed with M6-09; M6-10 delivered the metric language on top of it: pipelines and `unwrap` execute inside range aggregations (client-aggregated over a full-window raw scan — **complete or a named "query too broad" error, never a silently truncated aggregate**; four independent bounds enforced before any over-cap allocation — the evaluation-bucket grid (11,000 buckets), the row-growing sample retention of the order-dependent reducers `quantile_over_time`/`rate_counter` (4,000,000 retained values each), and the query-lifetime bytes of those groups' retained label sets (256 MiB, charged before each first-seen group is inserted) — issue #236 DELETED the former mid-scan derived-series count cap (500 distinct output groups), which rejected a broad class of high-cardinality aggregations the reference serves, and moved the reference's `max_query_series` 500 to where the reference enforces it: the FINAL result of the whole expression. A query that scans 20,505 groups and aggregates to one series is now served, exactly as the reference serves it; intermediate aggregation output and binary operands are uncapped by count, bounded by bytes and points instead — each rejects the whole query rather than truncating it; un-piped count/bytes/rate RANGE aggregations now read raw and stream Loki's sliding windows too (issue #227) — the request-time `(end-start)/step > 11000` guard is Loki's own resolution limit, returning Loki's exact HTTP 400 rather than a 422), the full over-time set, `stddev`/`stdvar`/`topk`/`bottomk`, and binary operations (vector⊗scalar in both orientations, vector⊗vector and matrix⊗matrix with `bool`, `and`/`or`/`unless`, and — issue #91 — the full `on`/`ignoring`/`group_left`/`group_right` vector-matching modifiers, semantics oracle-verified against `grafana/loki:3.4.2` and applied per step for range vectors). One-to-one matching output carries the reduced (`on`/`ignoring`) signature; `group_left`/`group_right` pass the many side through whole and copy the include labels from the one side; a cardinality violation is the reference's exact `many-to-one matching must be explicit` / `many-to-many matching not allowed` error. Streams-path error series carry both `__error__` and its human-readable `__error_details__` companion (issue #99), byte-exact against `grafana/loki:3.4.2` for the representative `JSONParserErr`/`LogfmtParserErr`/`LabelFilterErr` classes and faithful-format for the value-interpolated long tail (ledgered in docs/benchmarks/logs-differential-ledger.md); the metric pipeline-error path is unchanged. The `__error__`/`__error_details__` pair is held **out-of-band** exactly as the reference holds it (two plain string fields on the label builder, never ordinary label entries; empty means unset), merged into the emitted set once, gated on the builder-dirty bit — with the reference's observable consequences (issue #238, all live-probed at v3.7.4): a `label_format` rename cannot see the pair (its source resolves from the label set only, so `label_format x=__error__` is a no-op on an errored line, while a parser-extracted vector `__error__` does rename); assigning `__error_details__` on an errored line is masked by the slot; `drop __error__` resets only the err slot and never touches a same-named vector entry (the orphaned details stay invisible on a clean builder and re-surface on any label add/delete — including per-entry structured metadata, whose reserved-named entries route into the slots after the `_extracted` collision suffix); `keep` always retains `__error__`/`__error_details__`/`__preserve_error__`; string `__error__` filters and `drop` matchers read the slot while `__error_details__` filters read the vector; `ip(...)` passes an errored line unconditionally; and a numeric-filter failure never overwrites an earlier error (first error wins). `label_format x=x` net-deletes a resolved label (the reference's `Set`-then-`Del` order), and the sole ratified residual is the doubly-populated metric error message (`error-pair-duplicate-slot` in the ledger). A metric line that retains a nonempty `__error__` after its pipeline (e.g. a failed `unwrap` conversion with no `__error__` filter) fails the query with the reference store's exact `pipeline error: ...` surface, oracle-verified. `first_over_time`/`last_over_time` in **range** queries select the endpoints of Loki's canonical `(timestamp, stream_hash, tie_rank)` window order (issue #227 — Loki-exact cross-stream via `StableHash`, with the ratified same-stream `tie_rank` divergence above); in **instant** queries they retain the pinned, input-order-independent value-tiebreak (smallest (first) / largest (last) at the boundary timestamp — the reference's tie order there is unspecified, so PulsusDB pins determinism). Line filters placed before any parser/`line_format` keep their skip-index pushdown byte-identically — parsers run only on the index-reduced row set. Range-query metric aggregation uses Loki's **sliding** `[range]` windows (issue #227 — resolving the former tumbling divergence): the window `(t-range, t]` is re-evaluated at every start-anchored grid point `{start + k·step ≤ end}`, streamed off raw `log_samples` (the 5s rollup fast-path is retired for range reads — it cannot reproduce Loki's per-event boundary), so `rate({}[1m])` and `rate({}[10m])` now differ and graphs match Loki. Same-timestamp cross-stream ordering is Loki-exact via `StableHash` (`xxhash64`, seed 0, over the sorted `name·0xFF·value·0xFF` stream labels); the one ratified divergence is same-nanosecond **same-stream** samples, ordered deterministically by full body bytes (a group-local `tie_rank`) rather than Loki's unstored chunk-insertion order — measure-rare, byte-stable across runs, and bounded by a `MAX_TS_COLLISION_GROUP` clean 422. Instant metric queries are unchanged (semantically identical to the reference). M8-LQ1 added the `unpack`/`decolorize`/`drop`/`keep` stages and the `logfmt` flags, and corrected the default `| logfmt` to the reference's lenient best-effort semantics — a malformed line NEVER sets `__error__` and empty-value pairs are dropped by default; `--strict` gates the `LogfmtParserErr` (for every malformed class) and `--keep-empty` retains empty-value pairs (resolving the pre-existing over-eager #72 default-trigger divergence). `unpack`/`decolorize` rewrite the line, so a line filter after them evaluates in-engine; `drop`/`keep` mutate only labels, so a following line filter still pushes down. With the M8-LQ closeout (#203) the whole documented LogQL surface is dispositioned: **LogQL conformance carries no tracked interim constructs (interim == 0)** — the two constructs the reference itself rejects (`distinct`/bare `ip`, which are not v3.7.4 pipeline stages) are recorded as `reject-parity`, the closeout allowlist is empty, and the strict gate enforces it against the pinned v3.7.4 reference. Issue #221 adds `approx_topk(k, ...)`: probabilistic top-k via a byte-exact port of the reference's count-min sketch (27183×7 grid, FNV-1a32 + Jenkins double hashing, `stableBytes` keys, min estimator, xxh64 dedup-on-retention, 10 000-label retention cap) — the reported value is always the sketch **estimate**, never the true value. It is instant-only (a range query is rejected with the reference's exact `count min sketches are only supported on instant queries` body — Loki surfaces it as a 500, PulsusDB as a 400 per the ledgered status-divergence precedent) and rejects grouping. Bit-exactness against the reference holds exactly where the reference is self-reproducible: ≤ 10 000 distinct inner series, no xxh64 retention-hash collision, no order-sensitive float sums in shared sketch cells, and no tie at the k-th boundary; above the retention cap the reference's own output depends on a randomized Go map walk (not reproducible even by itself), where PulsusDB instead pins a deterministic canonical insertion order — the same treatment as the instant `first_over_time`/`last_over_time` tie pin. The shared `k` validation is reference-exact for `topk`/`bottomk`/`approx_topk` alike (`k <= 0` and non-integer `k` are 400s; `topk(0, ...)` no longer returns an empty 200). Note: unlike the reference (which uses the sketch to shard/shrink fan-out), `approx_topk` does not reduce scanned data in PulsusDB — it is a parity/result-shape construct, and its intended high-cardinality use was formerly blocked by the mid-scan group cap, which issue #236 has now deleted. Issue #221 also adds `variants(<metricExpr>, …) of (<logRangeExpr>)` (multi-variant queries, reference-gated behind `limits_config.enable_multi_variant_queries` — PulsusDB ships the ENABLED configuration unconditionally, the `approx_topk`/`shard_aggregations` precedent): ONE scan with N reducers, never N queries — the common log range plans the single raw scan (byte-identical SQL to the equivalent single-extractor query, independent of N; always raw/client-aggregated, since the rollup cannot serve unwraps, per-variant `[range]` windows or the common pipeline), and every emitted series is tagged with the plain-decimal index label `__variant__`. Reference-exact semantics, all live-probed and container-captured (`b13_variants.test`): a variant's own selector, line filters and parsers are DEAD syntax (only its reducer, `[range]`, `unwrap` and post-`unwrap` filters run); a COMMON-range `unwrap` (and its post-filters) is dead syntax too (the common pipeline truncates at the first `unwrap`); each variant slides its OWN `[range]` on the shared grid while the scan window stays the common range's; `__variant__` is injected into an outer vector aggregation's grouping for BOTH `by` and `without` (a nil grouping becomes `by (__variant__)`; `sum without (env)` therefore STRIPS the index); a `__variant__`-less series is returned at instant and dropped at range (the reference's instant/range asymmetry); an `absent_over_time` variant's synthetic labels come from the variant's own (otherwise dead) selector; and `variants(…) of (…)` composes only as a top-level expression or binary operand (`sum(variants(…))` is a 400, `variants(…) + 1` a 200). Memory is charge-before-allocate end to end: every per-sub-state cap is `AggCaps::DEFAULT` divided by N (the per-field TOTAL over sub-states equals today's single-query bound), the fan-out's fixed state (compiled-pipeline arena — regex programs Arc-shared, never recompiled per variant — meta snapshots, driver buffers, per-variant plan clones) is charged against one 256 MiB budget before each allocation (`MAX_VARIANT_FANOUT_STATE_BYTES`, derived from `MAX_CLIENT_AGG_GROUP_BYTES` and moving with it — a SECOND counter beside the sub-states' own, which is why the composed bound below counts that cap twice), and the DERIVED backstop `MAX_VARIANT_SUB_STATES` (= the smallest divided cap's floor point, re-derived to 10,000 by issue #236 and UNREACHABLE at #279's 131,072-byte query-text cap, which admits at most 4,368 variants) is a clean 422 where the reference is unbounded. The deliberate divergences are ledgered (`variants-*` entries in docs/benchmarks/logs-differential-ledger.md): non-conforming variant shapes are one plan-time 400 where the reference 500s/nil-panics; a surviving `__error__` keeps PulsusDB's own consistent 400 where the reference 500s `unexpected empty result`; and a common-pipeline `__variant__` collision pins index-wins where the reference duplicates the label and provably mis-routes values. Issue #276 adds `label_replace(<metricExpr>, "dst", "replacement", "src", "regex")` — a full `metricExpr` alternative exactly as in the reference grammar (legal inside vector aggregations, parentheses, binary operands and itself), evaluated as a pure in-engine label transform over the operand's result (no scan of its own; SQL/pushdown untouched). Reference-exact and container-captured (`b16_label_replace.test`): the regex compiles once with Loki's `^(?:…)$` anchoring (no dot-all — deliberately NOT Prometheus's `^(?s:…)$`) through the #317 RE2→Rust rewrite; an absent source label reads as `""`; no match leaves the series untouched; a match deletes `dst` and re-sets it to the Go `ExpandString` expansion (`$1`/`${name}`, out-of-range group → empty, `$$` → literal), with an empty expansion leaving it deleted; the destination name is NOT validated (`"0bad"`, `"__name__"`, even `""` pass to the wire, as the reference does); instant collisions return duplicate samples unmerged while range collisions merge per label set with per-timestamp repeats. An uncompilable regex is a 400 whose message reports the WRAPPED `^(?:…)$` form — the reference's genuine per-site asymmetry (every other LogQL site reports the user's raw pattern; issue #240's do-not-touch note, now live and pinned by test). The two deliberate divergences are ledgered: a scalar-typed operand is a plan-time 400 where the reference 500s an internal type-assertion (`label-replace-scalar-operand-status`), and the merged-collision same-timestamp tie order is pinned deterministic where the reference's is an irreproducible Go map walk (`label-replace-collision-tie-order`). Issue #288 deduplicates repeated grouping labels to reference parity: `sum by (fp, fp) (…)` == `sum by (fp) (…)` for every aggregation, both grouping positions and the grouping `variants(...)` injects into — container-captured for every aggregation but `avg` (`b17_grouping_dedup.test`); `avg` is gated by the hermetic bit-for-bit equivalence test `avg_by_duplicate_grouping_equals_the_deduped_form`, whose reference-parity link is `b4_vector_aggs.test`'s captured `avg by (region)` row plus the default-config live probing of the duplicated form — the parser keeps the duplicates in the AST exactly as the reference's does (Display round-trips them), and the plan-time `VectorAggSpec` producer normalizes what evaluation sees; `on(...)`/`ignoring(...)`/`group_left/right(...)` lists were already set-semantic and are pinned so. The reference's own sharded-frontend `avg` breaks on this shape under our oracle config — which is WHY avg carries no captured corpus row — an oracle-config note (`grouping-dedup-avg-sharded-frontend`), not a divergence. Issue #230 replaces the former `{{.label}}`-only template subset with the reference's FULL `line_format`/`label_format` template engine: the complete Go `text/template` language (actions, pipelines, `$` variables, `if`/`else if`/`range`/`break`/`continue`/`with`/`define`/`template`/`block`, `{{- -}}` trimming, comments, `missingkey=zero`) plus exactly the 86 callable names the reference registers (19 text/template builtins + the 23-entry function map + per-line `__line__`/`__timestamp__` + the 42-name sprig subset — anything else, including sprig names the reference does not expose like `sha256sum`, rejects with Go's `function "x" not defined`), the full `printf` verb engine (flags, width/precision, `%[n]` indexes, and every malformed form `%!d(MISSING)`/`%!(NOVERB)`/`%!(EXTRA …)`/`%!(BADINDEX)`), sprig's decimal arithmetic (`addf 0.1 0.2` = `0.3`, `divf` at division-precision 16, `decimal division by 0` per line), `spf13/cast` coercions (`int "0x10"` = 16, errors swallowed to zero), Go reference-layout time formatting/parsing, and the `time.Time` method closure (38 callable methods + the five `goodFunc` signature rejects, `Duration`/`Month`/`Weekday`/`*Location` methods, `[]byte` verb semantics). A template COMPILE error is the reference's 400 (`invalid line template: template: line:1: …`); a template EXECUTION error is per-line — the query succeeds, the line keeps flowing with `__error__="TemplateFormatErr"` and the engine's `template: <name>:<line>:<byte-col>: executing …` detail (line preserved for `line_format`; destination unset, last error wins, once-per-stage-frozen data map for `label_format`). 688 container-captured corpus directives (678 `eval` + 10 `eval_fail` across `t1…t6_*.test`, including the round-2 `fromJson` invalid-UTF-8/lone-surrogate parity captures) replay byte-exact hermetically — values AND error strings; the complete residual set (pinned heap-address cells, loaded-zone tzdata-table dumps, the 250-deep unified evaluator recursion cap and the 40-deep structural parse cap — both measured stack floors where the reference relies on growable goroutine stacks, with Go's own `max expression depth exceeded` text at the parse cap — rust-regex compile-error wording, `Local`-zone environment residuals) is ledgered under `template-*` in docs/benchmarks/logs-differential-ledger.md, with the address-cell exclusion re-derivable via `cargo run -p xtask -- template-audit`. The `{{.label}}` shapes keep their pre-existing single-allocation fast path (compile-time derived, allocation-gated), pushdown/planning are untouched, and full-engine templates cost nothing on queries that do not use them. Render memory is charge-before-allocate: every RETAINABLE production — multiplier outputs (`repeat`'s count×len, `indent`/`align` padding, `printf` widths/precisions, replace-expansion, `fromJson` trees, layout expansion), print-family/escaper buffers, action output, dynamic regex programs (a 1 MiB size_limit ceiling per per-line compile) and plain input-bounded copies (`__line__`, trims/slices, `default` clones — the round-2 fifth amplification class, which repeats or compounds inside no-output `range`/variable bodies) — charges a cumulative 64 MiB per-ROW budget (`MAX_TEMPLATE_RENDER_BYTES`, a standalone constant asserted at compile time to stay `<= MAX_CLIENT_AGG_GROUP_BYTES`) before allocating — one budget shared by every render a row performs, the `line_format` rewrite and each `label_format` destination alike, because each of those outputs is RETAINED; issue #260 moved that lifetime off the individual render, where the cap bounded one live buffer while the destination count (and so the number of live 64 MiB buffers) was bounded only by the 131,072-byte query-text cap, mechanically enforced by a runtime charge-dominance + ordering gate over every registry function's branch shapes (an AST census tripwires new/changed allocation sites); a breach is the bounded `422 query_too_broad` where the reference is unbounded and OOMs (ledgered `template-output-budget` — the reference being wrong is not copied). Interim divergence (#255): label-filter **parenthesis nesting** deeper than 90 levels (`| ((((x="1"))))`) is rejected with a 400 where the reference serves far deeper nesting (live-probed to 65,000) — the guard bounds paren nesting only, never flat `or`/`and` term width, exists solely because the alternative was a process-aborting stack overflow. It **stands after #272**: that issue converts the AST/plan walks (`Debug`/`Clone`/`PartialEq`/`Hash`/`Display`/drop and the planner/executor walks) to iterative form, but the parser's own recursive descent — which is what this guard bounds — is untouched. **#256 owns removing it**, alongside the depth-64 metric-nesting divergence, and cannot simply raise it to the query-text cap (131,071 bytes of `(` is roughly 65,000 parser recursion levels): the parser must be converted or frame-bounded first. Still explicitly interim, with a named owner. **What #272 did close, measured on a 2 MiB stack, release:** the AST drop path now survives 65,535 terms / 131,069 bytes — the largest query the 131,072-byte cap admits — where it aborted at 33,000 terms; and a flat label-filter chain now survives **32,765 terms / 131,069 bytes** — the widest the cap admits, built from the cheapest valid term (`a>1` plus a one-byte comma-AND) — through parse, compile, per-row evaluation, `Debug`, `Clone` and drop, where compilation aborted at 3,000 terms / 33,696 bytes. **What #293 then closed (the last recursive walk):** `plan()` used to abort on a flat `rate(…) or rate(…) or …` chain — measured ok at 1,200 terms, `fatal runtime error: stack overflow` at 1,250, inside the query-text cap — because the planner's `build_metric_node` was the one walk #272 left recursive. It is now a `find_preorder` emission pass plus a reverse fold, and the widest chain the cap admits plans end to end on a **256 KiB** stack: 65,536 terms / 131,071 bytes of `1+1+…` (the cheapest admissible term, 131,071 planned nodes) and 3,855 terms / 131,066 bytes of #285's own `count_over_time(…) or …` shape, each driven through parse → plan → `Debug` → `Clone` → `PartialEq` → drop, paired with a control in which a per-node recursion over the same parsed chain at a quarter the width aborts on the same stack. With that, **no LogQL walk over the AST or the plan tree costs a machine-stack frame per node**; the parser's own recursive descent is untouched and stays bounded by the #255 guard #256 owns.

**LogQL keyword case (#339):** LogQL **keywords and function names are case-insensitive**, matching the reference's lexer — `RATE(...)`, `SUM BY (...)`, `| JSON`, `LABEL_REPLACE(...)`, `VARIANTS(...) OF (...)`, `> BOOL`, `+ ON (...) GROUP_LEFT (...)`, `| UNWRAP DURATION(v)` and `|= IP("...")` all parse and mean exactly what their lowercase spellings mean. **Identifier payloads are not folded** and stay byte-exact: label names in selectors, grouping lists, label filters, `drop`/`keep`, `label_format` sources/destinations and `unwrap`, plus label values and every string body. That asymmetry is the reference's own, verified semantically rather than by acceptance (a status probe cannot tell `Mixed` from `mixed`, since both parse): against the pinned reference container, `{App="cf"}` matches nothing where `{app="cf"}` matches, `| json | RATE="R"` matches nothing where `| json | rate="R"` matches, and `sum by (Env)` groups on `Env` while `sum by (env)` groups on nothing. Two token classes are deliberately case-**sensitive** for the same reason: the `logfmt` stage flags (`--strict`/`--keep-empty`; `--STRICT` is a reference 400) and range-selector duration units (`[5S]`/`[5M]`/`[5W]` are `unknown unit` there). Both directions are pinned in `crates/pulsus-logql/tests/case_folding.rs`, whose verdicts were captured from that container and are replayed against it by a CI differential leg.

**LogQL query-text cap (#279):** LogQL query source of **131,072 bytes or more** is rejected `400 bad_data` before tokenization (`pulsus_logql::MAX_QUERY_BYTES`, an exclusive maximum — the longest accepted query is **131,071 bytes**, counted in bytes not chars); the value and `>=` boundary are the reference's `maxInputSize` (grafana/loki v3.7.4 `pkg/logql/syntax/parser.go:42`, enforced at `:86`). Applies at every LogQL entry point by construction (the lexer only accepts cap-checked input), including per `match[]` value on `/series` and `/tail`'s params. On the wire that rejection is reachable only through the POST form surfaces: `http::Uri` caps a request-target at 65,534 bytes, so a GET carrying a query anywhere near the cap is answered `414 URI Too Long` by hyper before routing, where the reference serves it — a measured transport-layer divergence, ledgered as `get-request-target-uri-bound` in docs/benchmarks/logs-differential-ledger.md. Distinct from the 8 MiB rendered-SQL cap (`pulsus_read` `MAX_QUERY_TEXT_BYTES`), and it does NOT relax the parser depth guards (#255/#272).

**TraceQL query-text cap (#284):** a TraceQL expression of **more than 131,072 bytes** is rejected `400 bad_data` at parameter parsing (`traces_api::querytext::MAX_QUERY_EXPRESSION_BYTES`, an **inclusive** maximum — exactly 131,072 bytes is ACCEPTED and 131,073 is the shortest rejected, counted in bytes not chars). Value and boundary are the reference's: grafana/tempo v3.0.2 defaults `max_query_expression_size_bytes` to `128 * 1024` (`modules/frontend/config.go:141`) and its query-frontend validator compares `len(traceQLQuery) > cap` (`modules/frontend/pipeline/async_query_validator_middleware.go:45`) — note the `>`, the opposite edge to LogQL's `>=` on the same number. SCOPE matches the reference too: the cap measures the `q`/`query` **parameter** on search and TraceQL metrics — the three pipelines that carry the validator (`modules/frontend/frontend.go:159` search, `:215` query_range, `:229` query_instant), which reads `q` then `query` on **all three**, search included — never the tag-discovery or trace-by-ID routes, and never the expression the LEGACY `tags`/`minDuration`/`maxDuration` params compile to — legacy compilation expands its input by up to ~2.5x and can cross the cap on its own, so capping it would manufacture a rejection the reference does not have. Tempo's parser (`pkg/traceql`) carries no length guard at all, which is why the check is at the parameter and not in `pulsus-traceql`. On search, `query` is capped but is **not** an alias for `q` — the reference's search request parser reads `q` alone (`pkg/api/http.go:180`) and folds a lone `query` into its legacy tag map — so capping it changes no search semantics. The one deliberate divergence: the reference selects last-write-wins, so an over-cap `q` shadowed by an under-cap `query` skips its cap and is then executed unbounded; PulsusDB caps both parameters and rejects that shape. Enforced by construction: the search/metrics parameter structs hold a `TraceQlText` whose only constructor is the length check. **Not reachable over the wire today:** every TraceQL route is `GET`-only and `http::Uri` rejects a request target above 65,534 bytes (measured), so the HTTP stack answers such a request before routing where the reference serves it — the same sub-cap transport band filed as #296 for LogQL.

**TraceQL search `query` parse-validation (#326):** the same query-frontend validator does **two** things to the parameter it selects, and #284 shipped only the first. After the size check at `modules/frontend/pipeline/async_query_validator_middleware.go:45` it runs `traceql.ParseNoOptimizations` (`:49`) and then `traceql.Validate` (`:51`), wrapping any failure as `invalid TraceQL query: …` (`:54`) into the `400` of `NewBadRequest` (`modules/frontend/pipeline/responses.go:69`). On the metrics routes that changes nothing for PulsusDB — `q`/`query` are aliases there and the handler parses whichever it selected. On **search** it does: `query` is validated by the reference but never read as an expression by its request parser (`pkg/api/http.go:180` reads `q` alone), so nothing downstream had ever looked at it here and `GET /api/traces/v1/search?query=<malformed>&start=…&end=…` was a `200`. It is now a `400 bad_data` carrying the reference's `invalid TraceQL query: ` prefix and a `position` byte offset — and `query` is still **not** an alias for `q`, exactly as under the cap. The ordering is reproduced as well as the checks: a value that is both over-cap and unparseable is rejected on LENGTH, because `:45` returns before `:49` runs. **Unlike the cap this is reachable over the wire today** — a malformed expression is short, so the 65,534-byte `http::Uri` request-target bound (#296) does not intercept it. **The `traceql.Validate` half is reproduced too (#328):** `pulsus_traceql::validate` is a route-independent port of the reference's semantic pass (operand-type agreement, per-type operator sets, regex literals through the shared `pulsus-re2` verdict, the intrinsic `= nil` rule, quantile bounds, `by(...)` arity, `topk`/`bottomk` limits, `compare()` exclusivity), run after parse and before planning on `q`, on search's shadow `query`, and on the metrics parameter alike — deliberately NOT the planner, which is stricter (`{} | rate()` validates everywhere and still plans only on the metrics routes). Every accept/reject decision is container-captured (`validate-vectors.json`, re-verified live in CI, fail-closed). The narrowed residual (#336): the regex verdict is three-valued and `Unknown` is accepted, so patterns only a real RE2 can adjudicate — the class families enumerated from `pulsus-re2`'s own return sites and measured per class: lookarounds (the commonest member), out-of-table `\p{…}` properties, `\u`/`\U` escapes, a trailing backslash, non-portable `(?…` heads, over-1000 or chained repetitions, over-budget compilations — are accepted on the validation-only shadow `query` where the reference 400s (storage-bound paths still reject at execution via ClickHouse's RE2); ledgered with the full class table as `traceql-validate-re2-unknown-residual`, plus the `traceql-validate-nil-spelling-conflation` row for the exotic `!(x != nil)` spelling the parser cannot distinguish from `x = nil`.

**LogQL per-query retained-byte bound (#260):** every ceiling above is enforced by a single gate FUNCTION, but not always by a single COUNTER — one metric leaf can hold two live counters against the same cap at once (`{slider, fold}` on a folded range query, `{fan-out, Σ sub-states}` on a `variants(...)` query), so what a cap proves is the SUM over its live counters, not the cap. That sum is published rather than left implicit: **`MAX_LEAF_RETAINED_BYTES` = 1,953,259,520 B (1.819 GiB)** — 2 × 256 MiB of group bytes, 4,000,000 × 32 B of window retention, 4,000,000 × 8 B of `quantile_over_time` values, 4,000,000 × 16 B of `rate_counter` points, one 8 MiB collision-staging group, and the two result-point counters at their own slot widths (12,000,000 × 16 B and 12,000,000 × 24 B) — every fixed-width term priced through the codebase's own 2× allocator-rounding model. **`MAX_QUERY_RETAINED_BYTES` = 2,087,477,248 B (1.944 GiB)** adds ONE row's per-row output budgets — 64 MiB of template render output and 64 MiB of `| json` flattened keys, which add rather than share because a single row can hold both at once. Both constants are DERIVED at compile time from the caps, the slot widths and a counter-multiplicity table (`CounterPlurality`), so raising any cap, widening any slot or changing a multiplicity moves the number or fails the build. **What the compiler holds** is that every `AggCaps` axis — which is, by contract, every per-query retention cap in one place — has both a multiplicity and a term, and that every LISTED per-row budget has a term: the caps, the multiplicities and the `RowBudgets` table are DESTRUCTURED with explicit field lists inside the derivations themselves, so a new axis or a new listed budget is a build failure rather than a missing term. (#260 shipped the row term as a free-standing `+ template` addend with no enumeration behind it; #287's second per-row ledger was consequently added, reviewed and committed without appearing in the published figure. The derivation was complete over the `AggCaps` axes and over nothing else, while the published claim covered the whole per-query figure — corrected here.) **What it does not hold**, said plainly: that a declared multiplicity is the true one, that a counter enforcing a cap through a destructured or aliased read is listed, and — the front half of the per-row axis — that a new per-row ledger acquires a term at all. Three routes still compile: a new `RowBudget` variant answered with `0`, one answered with an EXISTING `RowBudgets` field (the shape a careless author actually writes, verified by mutant), and a ledger that reuses a variant or reports through some other error type. Routes 1 and 2 leave a lexical trace and a census trips on them (`tests/logql_row_budget_enumeration.rs`, variants counted against fields); route 3 leaves none. Closing it properly would mean making a per-row ledger unconstructable except through one sealed type that reads its ceiling out of this table — the shape the template module already uses for render output — which is a cross-cutting refactor of both ledgers and is not attempted here. Two source censuses cover those as tripwires — every production `caps.<field>` read (which is what catches a counter charged inline rather than through a gate function) and every charge-gate call's counter expression — and they are lexical, so they are tripwires and not proofs. The counters are deliberately NOT collapsed into one pot: sharing them would save ~0.8 GB (the same operational band) at the price of rejecting the high-cardinality `sum by (…)` shapes issue #236 exists to serve. Stated residuals, not covered by this figure: accumulated leaf RESULTS across a binary chain (#257/#285), post-aggregation grouping keys (#241), the per-row template outputs a streams response accumulates across up to `max_entries_limit_per_query` entries (#312), and process RSS under concurrency, which is `N ×` the above and is an operational sizing concern rather than a per-query bound.

**LogQL pipeline exact fetch-until-limit (M6-09, #90):** pipelines containing an in-engine dropping stage that cannot push down (a label filter, or a line filter after `line_format`) are served by keyset-cursor paging: the engine pages `reader.logql_pipeline_scan_factor × limit` rows at a time (default factor 10) through the pipeline until the true `limit` fills, the query window is exhausted, or the byte scan budget is spent. Responses fill exactly to `limit` (no under-return) and never over-return; the fast/non-dropping paths keep a single byte-identical `LIMIT` scan. The byte scan budget (`reader.logql_scan_budget_bytes`) is the hard cumulative scan ceiling and aborts first — a budget-truncated result returns the survivors so far and signals incompleteness via `data.stats.pulsus_partial` (configuration.md §6, api.md §2.1/§2.2).

**Read-path differentiators:** token/ngram skip indexes accelerate line filters (no full body scans within the selected streams); stream-selector-bounded scans otherwise; per-query scan budget with explicit "query too broad" errors instead of OOM.

With this the whole OTLP span-event / span-link / instrumentation-scope set is indexed and searchable: **TraceQL conformance carries no tracked interim constructs (interim == 0)** — the #185 closeout allowlist is empty and the strict gate enforces it.
