# PulsusDB Features & Compatibility Matrix

This document enumerates every feature PulsusDB commits to and the milestone in which it lands. It is the source of truth for scoping GitHub issues — every row here should trace to one or more issues.

Two product decisions frame the matrix:

1. **The OpenTelemetry Collector is the ingestion path.** Logs, metrics, traces, and profiles arrive via OTLP (metrics alternatively via the collector's Prometheus remote-write exporter). OTLP endpoints are always on and land with each signal's milestone. Foreign push protocols are optional compatibility receivers, off by default.
2. **The PulsusDB API is product-neutral.** Primary query paths live under `/api/{logs,traces,profiles,rules}/v1/...` plus the standard Prometheus HTTP API for metrics. Third-party API surfaces (log/trace/profile datasource protocols) are flag-gated aliases (`PULSUS_COMPAT_ENDPOINTS`) onto the same handlers — see [api.md §8](api.md).

Milestones: **M0** scaffolding · **M1** logs proof · **M2** metrics proof · **M3** downsampling · **M4** traces · **M5** profiles · **M6** full language compliance + compat ingest breadth · **M7** native histograms + operations. See §7.

M1 and M2 are deliberately **narrow proof milestones**: the project exists because reads are slow, so the earliest code must validate the storage and planner design against captured real-world slow queries — full language parity comes in M6, after the read path has earned it with benchmark evidence.

## 1. Ingestion

### 1.1 Primary (always on)

| Protocol | Endpoint | Formats | Milestone |
|----------|----------|---------|-----------|
| OTLP logs | `POST /v1/logs` | protobuf | M1 |
| OTLP metrics | `POST /v1/metrics` | protobuf (exponential histograms flatten to classic `_bucket`/`_sum`/`_count` series until native-histogram storage lands in M7) | M2 |
| OTLP traces | `POST /v1/traces` | protobuf | M4 |
| OTLP profiles | `POST /v1development/profiles` | protobuf (experimental OTLP signal) | M5 |
| Prometheus remote write | `POST /api/v1/write` | snappy protobuf (`prompb.WriteRequest`) — supports the collector's `prometheusremotewrite` exporter | M2 |
| Profile ingest (native) | `POST /api/profiles/v1/ingest` | pprof | M5 |
| OTLP/JSON encoding | all OTLP endpoints | JSON per OTLP/HTTP spec | M6 |

### 1.2 Compatibility receivers (flag-gated, M6)

`POST /loki/api/v1/push` (JSON/protobuf) · Zipkin `POST /tempo/spans`, `/api/v2/spans` · `POST /ingest` (pprof alias, ships M5) · InfluxDB line protocol `POST /influx/api/v2/write` · Datadog `POST /api/v2/logs`, `/api/v2/series` · Elastic `POST /_bulk`, `/{target}/_bulk`, doc endpoints · remote-write path aliases.

### 1.3 Cross-cutting ingest features (M1 onward)

gzip/snappy/zstd request decompression · sync/async insert selection per request (`X-Pulsus-Async`) · per-request database routing (`X-Pulsus-Database`) · bounded buffering with `429` backpressure · per-protocol ingest metrics. Retention is per-table/database configuration; there is deliberately no per-write TTL override in v1.

**LogQL — M1 proof subset:** stream selectors with `=`, `!=`, `=~`, `!~`; line filters `|=`, `!=`, `|~`, `!~`; range aggregations `rate`, `count_over_time`, `bytes_rate`, `bytes_over_time`; vector aggregations `sum`, `avg`, `min`, `max`, `count` with `by`/`without`. This subset is exactly what's needed to prove the read path: index-served stream resolution, skip-index line filters, and rollup-served counts.

**LogQL — structured metadata on the metric path (issue #249):** a metric
query merges each entry's per-entry structured metadata into that sample's
label set, before any pipeline stage runs, as the reference's sample
extractors do (`pkg/logql/log/metrics_extraction.go:102-104` and `:202-205 @
v3.7.4`) — so `sum by (trace_id) (count_over_time({app="x"}[5m]))` groups by
metadata, a label filter filters on it, and `line_format`, `label_format`,
`unwrap`, `drop` and `keep` read it. A colliding key is renamed
`<key>_extracted` by the SAME merge the streams path uses, so the two
surfaces cannot resolve a collision differently, and a reserved
`__error__`/`__error_details__` routes to the out-of-band slot exactly as
there. One stream therefore yields one output series per distinct metadata
combination, and `absent_over_time` remains metadata-blind because the
reference makes it so (`syntax/extractor.go:46-47`). A filter on a metadata
label is evaluated in the compiled pipeline, never pushed into SQL — see
docs/schemas.md §3.2 for what that costs and for the one performance cliff
it introduces.

**LogQL — parity (M6):** parsers `json`, `logfmt` (with the `--strict`/`--keep-empty` flags — M8-LQ1), `regexp`, `pattern`; the `unpack`, `decolorize`, `drop`, and `keep` pipeline stages (M8-LQ1); a `| logfmt <label>="<expression>"` targeted extraction accepts exactly the shape the reference's own extraction-expression sub-grammar accepts (issue #247) — an optional leading bare key `[A-Za-z_][A-Za-z0-9_]*` followed by any number of `"…"` strings, so `a="b.c"`, `a="b-c"`, `a="b c"` and `a=""` are a `400` here as they are there, and a comma in an extraction list must be followed by another entry (for `json` as well as `logfmt`); a `| json <label>="<expression>"` targeted extraction likewise accepts exactly the shape the reference's OWN json sub-grammar accepts (`pkg/logql/log/jsonexpr/` @ v3.7.4, a different grammar from logfmt's — issues #394/#388), so `v="b c"`, `v="b-c"`, `v="b]"`, `v="b.0"` and `v="b 1.5"` are a `400` here as they are there, while `v="arr[ 0 ]"`, `v="b[ \"c\" ]"` and `v="[ \"b-c\" ]"` are SERVED — whitespace is skipped between every token, which PulsusDB used to refuse, and a whitespace-bearing expression resolves to the reference's path so `v="b . c"` reads `["b","c"]`; the one capability withdrawn is a JSON key containing `]`, which the reference cannot address either (ledgered as `json-expression-bracket-key-unreachable`); a `| pattern "…"` argument accepts exactly the shape `pattern.New` accepts (`pkg/logql/log/pattern/` @ v3.7.4, a third grammar — issue #388), so a repeated capture name (`<a> <a>`), two adjacent captures, a pattern with no NAMED capture and an empty pattern are a `400` here as they are there, and a capture name is `[A-Za-z_][A-Za-z0-9_]*` rather than `[A-Za-z0-9_]+`, so `<1a>` is literal text on both sides where PulsusDB used to make it a capture and answer under a label the user never wrote; unlike the two expression sub-grammars a pattern rejection is raised at `ParseExpr` on the reference and is therefore refused in EVERY window; what a SURVIVING `| logfmt <label>="<expression>"` then evaluates to follows the reference's expression parser (`pkg/logql/log/parser.go:531-624` @ v3.7.4) rather than a per-expression lookup (issue #393) — every destination identifier is set to the empty string BEFORE the line is read, so a miss emits `<label>=""` rather than nothing (and `--keep-empty` has no bearing on it: the expression parser carries no such field, so the empty label appears with or without the flag); the LINE key is sanitized to `[A-Za-z0-9_]` with a `_` prefixed to a leading digit before it is compared, so `| logfmt a="b_c"` reads a `b.c=` pair and `| logfmt a="_1x"` reads a `1x=` pair; the pass is a single document-order scan with LAST write wins, so over `b=2 a=1` the query `| logfmt a="b"` answers `a="1"`; a destination identifier itself aliases a line key of that name, so `| logfmt a="x", b="nosuch"` over `b=1 a-b=2 x=3` answers `a="3", b="1"`; a repeated identifier keeps only its LAST source key; and a value containing `U+FFFD` is emptied on this arm where the bare `| logfmt` parser maps it to a space. Where two DIFFERENT identifiers name one source key the reference iterates a Go map and has no answer at all (measured: both outcomes occur across repeats of one query); PulsusDB breaks the tie by QUERY ORDER, ledgered as `logfmt-expression-duplicate-source-key-tiebreak`. Reading a JSON value out of a log line follows the reference's scanner rather than a strict parse (issue #389) — bytes AFTER a complete first value are ignored, so `{"a":1}trailing` answers `a="1"` at `| json`, `| json <id>="<path>"` and `| unpack` alike; the targeted form carries the reference's own gates (an empty line writes no label, a first byte outside `"`/`{`/`[` is `__error__="JSONParserErr"` with no detail, and any other miss is the empty-string fill rather than an error); and a targeted extraction that lands on an object or an array yields the DOCUMENT'S OWN BYTES — key order, duplicate keys, inner whitespace and escape spelling all preserved for an object, and the same span with the reference's `Unescape` run over it for an array — where PulsusDB used to re-render a parsed value; what remains is a line malformed INSIDE the value, which the reference's non-validating scan reads past and ours refuses, ledgered as `json-nonvalidating-scan-residual`; the same rule reaches a `variants(...)` variant's own pipeline, which is dead syntax at evaluation on both sides and validated anyway on both sides (the reference builds each variant's extractor purely to count it, `pkg/logql/evaluator.go:1417` @ v3.7.4); the whole accept/reject surface is committed point by point with the reference's verdict for each in `crates/pulsus-read/tests/logql_logfmt_expr_matrix.rs`, which re-measures it against the pinned container; **the regex accept surface is pinned the same way** (issue #246) — every LogQL construct that carries a user regular expression × the pattern classes where Go's `regexp` and the Rust `regex` crate disagree, each side's verdict committed and the reference's half re-measured live, in `crates/pulsus-read/tests/logql_regex_accept_matrix.rs`; a malformed pattern is a `400` on both sides at every one of the 864 probed points, the reference's Go-worded error text is deliberately NOT reproduced (owner ruling — nothing branches on it and byte parity needs a parser port), and the places where the two engines disagree about the DECISION rather than the wording are enumerated in `logql-regex-accept-surface-divergence` and owned by issue #400 — **whose Stage 2 (2026-08-12) emptied one whole direction of that table**: PulsusDB no longer SERVES any LogQL regex the reference refuses, because a reject-only pre-check built from the reference's own parser (`pulsus_re2::re2_definitely_rejects`) decides the constructs RE2 demonstrably rejects — a repetition of a repetition, a bound above 1000, a `(?x`/`(?u`/`(?R` flag, a `\u`/`\U` escape, an unknown POSIX class or Unicode property name, an inverted `[X--Y]` range, a capture name outside `[A-Za-z0-9_]` — before any engine compiles them, so `a**` no longer returns the whole stream where the reference sends a `400`; what remains open is the opposite direction and the wrong-rows class-algebra family; label filters (string + numeric with duration/bytes units); `line_format`, `label_format`, `unwrap`; full over-time set (`sum/avg/min/max/stddev/stdvar/quantile/first/last/absent_over_time`); `stddev`, `stdvar`, `topk`, `bottomk` vector aggregations; binary operations between range vectors; the `offset <duration>` range-selector modifier (issue #343 — `(T - d - range, T - d]`, and **signed**: the reference accepts a negative offset and shifts the window FORWARD, which PulsusDB reproduces). A shift that leaves the representable timestamp axis (`T - d` outside `i64`) answers **empty** rather than clamping onto the `i64` rail — clamping relocated the evaluation, so a query about 2026 scanned from 1977-01-08 — and it is still a 200, never a new rejection; the reference's own plain `int64` subtraction wraps there instead, and the residual shapes where empty is not the exact answer either are ledgered as `offset-domain-edge-exact-arithmetic`. **Nothing in a LogQL query may span more than 5 years** (43,800 h = 5 × 365 d): the `offset` magnitude in either direction, the `[range]` selector, and the query's own `start`-to-`end` span are each a `400 bad_data` past that, echoing the value sent rather than clamping it (an instant query has no span; its window is bounded by the capped `[range]`). That is a deliberate divergence, taken because retention is days to months, so it refuses nothing a real deployment does while removing the absurd-input arithmetic class entirely; ledgered as `five-year-span-cap`. **The reference's own bounds are narrower than this paragraph used to claim** — it said the reference "bounds no query span at all", which issue #248's live re-measurement refuted: `max_query_length` defaults to `721h` (`30d1h`, `pkg/validation/limits.go:371` @ v3.7.4, enforced `pkg/querier/queryrange/limits.go:194-201`), and the window it measures is `[start - ([range] + offset), end - offset]` (`pkg/querier/queryrange/shard_resolver.go:94-104` @ v3.7.4), so a range query's `[range]` literal counts against it while the `offset` cancels. Measured on the pinned v3.7.4 oracle: a `721h1s` request span and a `[720h]` selector over a `1h` request span are both `400 the query time range exceeds the limit`, so on those two axes the reference's default config refuses far MORE than our 5-year cap does; there is no dedicated `[range]` cap (`max_query_range` defaults to `0s`). What is genuinely ours is the `offset` magnitude — a `200` there at every value in the `i64` domain SAVE `i64::MIN` itself, which inverts the frontend's window through Go's negation overflow and is a `400 this data is no longer available` on any frontend that has not already answered its one-nanosecond neighbour (and in every probe order once `cache_index_stats_results` is turned off; at its shipped default the neighbour's cached index-stats entry answers a later probe `200`). That is an overflow artefact at a single value, not a magnitude bound — `i64::MIN + 1` is a `200` in any order — so past 43,800 h our cap is the only refusal by size WITHIN THE BAND THE REFERENCE'S LEXER ADMITS — `i64` nanoseconds, the negative endpoint aside. A magnitude too large for that band is refused by the reference too, at the lexer, and so is reject parity rather than a divergence: `offset 9223372036854775808ns`, `offset 18446744073709551615ns` and `offset -9223372036854775809ns` are all measured `400 … syntax error` there, and all three are 400s here (issue #248 rounds 6 to 8; the order-dependent probe table is in the `five-year-span-cap` ledger row) — and an instant query's `[range]`, which the reference admits and then splits into per-hour subqueries that do not answer in practice. Range aggregations read raw and slide (issue #227), giving up the 5s rollup speedup for bit-exact Loki parity; the configurable-resolution rollup remains for instant/other uses. The stream (log) pipeline landed with M6-09; M6-10 delivered the metric language on top of it: pipelines and `unwrap` execute inside range aggregations (client-aggregated over a full-window raw scan — **complete or a named "query too broad" error, never a silently truncated aggregate**; four independent bounds enforced before any over-cap allocation — the evaluation-bucket grid (11,000 buckets), the row-growing sample retention of the order-dependent reducers `quantile_over_time`/`rate_counter` (4,000,000 retained values each), and the query-lifetime bytes of those groups' retained label sets (256 MiB, charged before each first-seen group is inserted) — issue #236 DELETED the former mid-scan derived-series count cap (500 distinct output groups), which rejected a broad class of high-cardinality aggregations the reference serves, and moved the reference's `max_query_series` 500 to where the reference enforces it: the FINAL result of the whole expression. A query that scans 20,505 groups and aggregates to one series is now served, exactly as the reference serves it; intermediate aggregation output and binary operands are uncapped by count, bounded by bytes and points instead — each rejects the whole query rather than truncating it; un-piped count/bytes/rate RANGE aggregations now read raw and stream Loki's sliding windows too (issue #227) — the request-time `(end-start)/step > 11000` guard is Loki's own resolution limit, returning Loki's exact HTTP 400 rather than a 422), the full over-time set, `stddev`/`stdvar`/`topk`/`bottomk`, and binary operations (vector⊗scalar in both orientations, vector⊗vector and matrix⊗matrix with `bool`, `and`/`or`/`unless`, and — issue #91 — the full `on`/`ignoring`/`group_left`/`group_right` vector-matching modifiers, semantics oracle-verified against `grafana/loki:3.4.2` and applied per step for range vectors). One-to-one matching output carries the reduced (`on`/`ignoring`) signature; `group_left`/`group_right` pass the many side through whole and copy the include labels from the one side; a cardinality violation is the reference's exact `many-to-one matching must be explicit` / `many-to-many matching not allowed` error. Streams-path error series carry both `__error__` and its human-readable `__error_details__` companion (issue #99), byte-exact against `grafana/loki:3.4.2` for the representative `JSONParserErr`/`LogfmtParserErr`/`LabelFilterErr` classes and faithful-format for the value-interpolated long tail (ledgered in docs/benchmarks/logs-differential-ledger.md); the metric pipeline-error path is unchanged. The `__error__`/`__error_details__` pair is held **out-of-band** exactly as the reference holds it (two plain string fields on the label builder, never ordinary label entries; empty means unset), merged into the emitted set once, gated on the builder-dirty bit — with the reference's observable consequences (issue #238, all live-probed at v3.7.4): a `label_format` rename cannot see the pair (its source resolves from the label set only, so `label_format x=__error__` is a no-op on an errored line, while a parser-extracted vector `__error__` does rename); assigning `__error_details__` on an errored line is masked by the slot; `drop __error__` resets only the err slot and never touches a same-named vector entry (the orphaned details stay invisible on a clean builder and re-surface on any label add/delete — including per-entry structured metadata, whose reserved-named entries route into the slots after the `_extracted` collision suffix); `keep` always retains `__error__`/`__error_details__`/`__preserve_error__`; string `__error__` filters and `drop` matchers read the slot while `__error_details__` filters read the vector; `ip(...)` passes an errored line unconditionally; and a numeric-filter failure never overwrites an earlier error (first error wins). Issue #248 matches the reference's position-dependent handling of a MALFORMED `ip()` PATTERN, where PulsusDB used to reject everywhere: the reference's `NewIPLabelFilter` cannot fail — it records the error on the node and leaves the matcher nil (`pkg/logql/log/ip.go:94-103` @ v3.7.4) — and the only caller of `PatternError()` is `LabelFilterExpr.Stage()` (`pkg/logql/syntax/ast.go:801-809` @ v3.7.4), which type-switches on the stage's WHOLE filterer. So `| addr = ip("nope")` is a 400 (parentheses transparent), while the same filter nested under `and`/`or`/`,` is a 200, and so is a post-`unwrap` filter in EVERY position including a lone one (`Unwrap.PostFilters` is reduced with `ReduceAndLabelFilter`, `pkg/logql/syntax/extractor.go:76,187` @ v3.7.4, which never calls `Stage()`). A deferred filter is not dropped: it evaluates to `true` on an entry carrying a pipeline error and `false` on every other, for `=` AND `!=` alike, because `filterTy`'s `HasErr` and nil-matcher checks both precede the operator switch (`ip.go:123-145` @ v3.7.4) — container-captured in `b20_nested_ip.test`. Both label-filter sites the reference's grammar has are covered: `git grep -n labelFilter v3.7.4 -- pkg/logql/syntax/syntax.y` returns the `%type` declaration, the production itself, and exactly two uses — line 221 (a pipeline stage) and line 160 (a post-`unwrap` filter). **A label filter's error state is carried left to right, and every leaf to the right of a failed conversion sees it.** The reference's numeric-family filters call `lbs.SetErr` at the failing leaf and return `true` (`pkg/logql/log/label_filter.go:313-319` @ v3.7.4 for the float family, `:182-188` bytes, `:250-256` duration), and `BinaryLabelFilter.Process` walks its operands on that same builder (`:90-98`) — so `| logfmt | n > 1 and addr = ip("nope")` over `n=bad` RETURNS the line (the `ip()` leaf takes `filterTy`'s `HasErr` branch), as does the same shape with a well-formed pattern or with `__error__ = "LabelFilterErr"` in that position. `or` short-circuits and `and` does not (`:92-94`), so a numeric filter to the right of a true `or` operand never runs and never sets the error: `| logfmt | b = "x" or n > 1` and `| logfmt | n > 1 or b = "x"` return the same entries, only the second carrying `__error__`. PulsusDB used to defer the error to the end of the filter, which dropped lines the reference keeps; both halves are container-captured in `b20_nested_ip.test`. `label_format x=x` net-deletes a resolved label (the reference's `Set`-then-`Del` order), and the sole ratified residual is the doubly-populated metric error message (`error-pair-duplicate-slot` in the ledger). A metric line that retains a nonempty `__error__` after its pipeline (e.g. a failed `unwrap` conversion with no `__error__` filter) fails the query with the reference store's exact `pipeline error: ...` surface, oracle-verified. `first_over_time`/`last_over_time` select the endpoints of Loki's canonical `(timestamp, stream_hash, tie_rank)` order in **both** range and instant queries (issue #227 for the sliding path, issue #344 for the instant one — Loki-exact cross-stream via `StableHash`, with the ratified same-stream `tie_rank` divergence above). Until #344 the instant reducer used a PulsusDB-specific value tiebreak (smallest first / largest last at the boundary timestamp) adopted on the stated premise that **the reference's instant tie order was unspecified**. That premise was FALSE and the claim is deleted rather than softened: the reference's instant queries run the same merged sample iterator, whose order is explicitly `(Timestamp, StableHash)` (`pkg/iter/sample_iterator.go:139-148` @ v3.7.4) with `first`/`last` its ends (`pkg/logql/range_vector.go:489-501` batched, `:818-844` streaming). The value rule therefore returned a WRONG VALUE — measured 7 where the reference answers 5 on a group merging two streams at one nanosecond — not a ratified divergence, and it is gone. Line filters placed before any parser/`line_format` keep their skip-index pushdown byte-identically — parsers run only on the index-reduced row set. Range-query metric aggregation uses Loki's **sliding** `[range]` windows (issue #227 — resolving the former tumbling divergence): the window `(t-range, t]` is re-evaluated at every start-anchored grid point `{start + k·step ≤ end}`, streamed off raw `log_samples` (the 5s rollup fast-path is retired for range reads — it cannot reproduce Loki's per-event boundary), so `rate({}[1m])` and `rate({}[10m])` now differ and graphs match Loki. Same-timestamp cross-stream ordering is Loki-exact via `StableHash` (`xxhash64`, seed 0, over the sorted `name·0xFF·value·0xFF` stream labels); the one ratified divergence is same-nanosecond **same-stream** samples, ordered deterministically by full body bytes (a group-local `tie_rank`) rather than Loki's unstored chunk-insertion order — measure-rare, byte-stable across runs, and bounded by a `MAX_TS_COLLISION_GROUP` clean 422. **Issue #344 changes instant metric queries in three ways**: `first_over_time`/`last_over_time` take the same `(timestamp, StableHash)` delivery order the sliding path uses (`pkg/iter/sample_iterator.go:139-148` @ v3.7.4) in place of PulsusDB's value-tiebreak, which returned a wrong value; a range aggregation's own `by`/`without` clause executes on them; and `avg_over_time` uses the reference's RANGE recurrence `mean += F/count - mean/count` (`pkg/logql/range_vector.go:379-401` batched, `:716-744` streaming @ v3.7.4) rather than the vector aggregation's `(F - mean)/count`, which the two disagree on in the last bits for about a quarter of inputs. M8-LQ1 added the `unpack`/`decolorize`/`drop`/`keep` stages and the `logfmt` flags, and corrected the default `| logfmt` to the reference's lenient best-effort semantics — a malformed line NEVER sets `__error__` and empty-value pairs are dropped by default; `--strict` gates the `LogfmtParserErr` (for every malformed class) and `--keep-empty` retains empty-value pairs (resolving the pre-existing over-eager #72 default-trigger divergence). `unpack`/`decolorize` rewrite the line, so a line filter after them evaluates in-engine; `drop`/`keep` mutate only labels, so a following line filter still pushes down. With the M8-LQ closeout (#203) the whole documented LogQL surface is dispositioned: **LogQL conformance carries no tracked interim constructs (interim == 0)** — the two constructs the reference itself rejects (`distinct`/bare `ip`, which are not v3.7.4 pipeline stages) are recorded as `reject-parity`, the closeout allowlist is empty, and the strict gate enforces it against the pinned v3.7.4 reference. Issue #221 adds `approx_topk(k, ...)`: probabilistic top-k via a byte-exact port of the reference's count-min sketch (27183×7 grid, FNV-1a32 + Jenkins double hashing, `stableBytes` keys, min estimator, xxh64 dedup-on-retention, 10 000-label retention cap) — the reported value is always the sketch **estimate**, never the true value. It is instant-only (a range query is rejected with the reference's exact `count min sketches are only supported on instant queries` body — Loki surfaces it as a 500, PulsusDB as a 400 per the ledgered status-divergence precedent) and rejects grouping. Bit-exactness against the reference holds exactly where the reference is self-reproducible: ≤ 10 000 distinct inner series, no xxh64 retention-hash collision, no order-sensitive float sums in shared sketch cells, and no tie at the k-th boundary; above the retention cap the reference's own output depends on a randomized Go map walk (not reproducible even by itself), where PulsusDB instead pins a deterministic canonical insertion order — the same treatment as the ratified same-nanosecond same-stream `tie_rank` order. (This sentence used to cite the instant `first_over_time`/`last_over_time` tie pin; issue #344 deleted that pin as a wrong value, so it is no longer an example of pinning against an irreproducible reference.) The shared `k` validation is reference-exact for `topk`/`bottomk`/`approx_topk` alike (`k <= 0` and non-integer `k` are 400s; `topk(0, ...)` no longer returns an empty 200). **LogQL keyword case (#339):** LogQL **keywords and function names are case-insensitive**, matching the reference's lexer — `RATE(...)`, `SUM BY (...)`, `| JSON`, `LABEL_REPLACE(...)`, `VARIANTS(...) OF (...)`, `> BOOL`, `+ ON (...) GROUP_LEFT (...)`, `| UNWRAP DURATION(v)` and `|= IP("...")` all parse and mean exactly what their lowercase spellings mean. **Identifier payloads are not folded** and stay byte-exact: label names in selectors, grouping lists, label filters, `drop`/`keep`, `label_format` sources/destinations and `unwrap`, plus label values and every string body. Two token classes are deliberately case-**sensitive** for the same reason: the `logfmt` stage flags (`--strict`/`--keep-empty`; `--STRICT` is a reference 400) and range-selector duration units (`[5S]`/`[5M]`/`[5W]` are `unknown unit` there). **A malformed LogQL query is refused in every time window (#380):** PulsusDB decides accept-vs-reject from the query alone — parsing and pipeline compilation both run before any I/O — so `{app="checkout"} | addr = ip("nope")` is a `400` whatever `start`/`end` you ask for. **The reference is not**: measured on the digest-pinned v3.7.4 oracle, that same query is a `400` over a window ending now and a `200` with no results over one ending 3 h ago, ten years ago, or at `start=0&end=1`. The boundary is `querier.query_ingesters_within` (3 h by default), not `max_query_lookback` (`0s` on the pinned config): past it the ingester leaves the query's path (`pkg/querier/intervals.go:32-38 @ v3.7.4`) and the store returns an empty iterator as soon as no chunk matches (`pkg/storage/store.go:491`) — before the pipeline is built at `:497`, which is where the pattern error would have been raised. It is specifically errors the PARSER accepts and the pipeline BUILDER rejects (a malformed `ip()` pattern, an unterminated `line_format` template, a duplicated `label_format` target); a plain syntax error is refused in both windows. **We do not copy this** (owner ruling, 2026-08-06): a user reads an empty `200` as "no logs matched" rather than "your query is broken", and the same typo should not get two different answers depending on the dates. Ledgered as `malformed-query-refused-in-every-window`.

**LogQL query-text cap (#279):** LogQL query source of **131,072 bytes or more** is rejected `400 bad_data` before tokenization (`pulsus_logql::MAX_QUERY_BYTES`, an exclusive maximum — the longest accepted query is **131,071 bytes**, counted in bytes not chars); the value and `>=` boundary are the reference's `maxInputSize` (grafana/loki v3.7.4 `pkg/logql/syntax/parser.go:42`, enforced at `:86`). Applies at every LogQL entry point by construction (the lexer only accepts cap-checked input), including per `match[]` value on `/series` and `/tail`'s params. On the wire that rejection is reachable only through the POST form surfaces: `http::Uri` caps a request-target at 65,534 bytes, so a GET carrying a query anywhere near the cap is answered `414 URI Too Long` by hyper before routing, where the reference serves it — a measured transport-layer divergence, ledgered as `get-request-target-uri-bound` in docs/benchmarks/logs-differential-ledger.md. Distinct from the 8 MiB rendered-SQL cap (`pulsus_read` `MAX_QUERY_TEXT_BYTES`), and it does NOT relax the parser depth guards (#255/#272).

**TraceQL query-text cap (#284):** a TraceQL expression of **more than 131,072 bytes** is rejected `400 bad_data` at parameter parsing (`traces_api::querytext::MAX_QUERY_EXPRESSION_BYTES`, an **inclusive** maximum — exactly 131,072 bytes is ACCEPTED and 131,073 is the shortest rejected, counted in bytes not chars). SCOPE matches the reference too: the cap measures the `q`/`query` **parameter** on search and TraceQL metrics — the three pipelines that carry the validator (`modules/frontend/frontend.go:159` search, `:215` query_range, `:229` query_instant), which reads `q` then `query` on **all three**, search included — never the tag-discovery or trace-by-ID routes, and never the expression the LEGACY `tags`/`minDuration`/`maxDuration` params compile to — legacy compilation expands its input by up to ~2.5x and can cross the cap on its own, so capping it would manufacture a rejection the reference does not have. Tempo's parser (`pkg/traceql`) carries no length guard at all, which is why the check is at the parameter and not in `pulsus-traceql`. On search, `query` is capped but is **not** an alias for `q` — the reference's search request parser reads `q` alone (`pkg/api/http.go:180`) and folds a lone `query` into its legacy tag map — so capping it changes no search semantics. **TraceQL search `query` parse-validation (#326):** the same query-frontend validator does **two** things to the parameter it selects, and #284 shipped only the first. **LogQL per-query retained-byte bound (#260):** every ceiling above is enforced by a single gate FUNCTION, but not always by a single COUNTER — one metric leaf can hold two live counters against the same cap at once (`{slider, fold}` on a folded range query, `{fan-out, Σ sub-states}` on a `variants(...)` query), so what a cap proves is the SUM over its live counters, not the cap. That sum is published rather than left implicit: **`MAX_LEAF_RETAINED_BYTES` = 1,953,259,520 B (1.819 GiB)** — 2 × 256 MiB of group bytes, 4,000,000 × 32 B of window retention, 4,000,000 × 8 B of `quantile_over_time` values, 4,000,000 × 16 B of `rate_counter` points, one 8 MiB collision-staging group, and the two result-point counters at their own slot widths (12,000,000 × 16 B and 12,000,000 × 24 B) — every fixed-width term priced through the codebase's own 2× allocator-rounding model. **`MAX_QUERY_RETAINED_BYTES` = 3,161,219,072 B (2.944 GiB)** sums every per-query RESULT budget — the metric leaf above plus `MAX_STREAMS_RESULT_BYTES` = 1,073,741,824 B (#312) — and adds ONE row's per-row output budgets — 64 MiB of template render output and 64 MiB of `| json` flattened keys, which add rather than share because a single row can hold both at once. Both constants are DERIVED at compile time from the caps, the slot widths and a counter-multiplicity table (`CounterPlurality`), so raising any cap, widening any slot or changing a multiplicity moves the number or fails the build. **What the compiler holds** is that every `AggCaps` axis — which is, by contract, every per-query retention cap in one place — has both a multiplicity and a term, and that every LISTED per-row budget has a term: the caps, the multiplicities and the `RowBudgets` table are DESTRUCTURED with explicit field lists inside the derivations themselves, so a new axis or a new listed budget is a build failure rather than a missing term. (#260 shipped the row term as a free-standing `+ template` addend with no enumeration behind it; #287's second per-row ledger was consequently added, reviewed and committed without appearing in the published figure. The derivation was complete over the `AggCaps` axes and over nothing else, while the published claim covered the whole per-query figure — corrected here.) **What it does not hold**, said plainly: that a declared multiplicity is the true one, that a counter enforcing a cap through a destructured or aliased read is listed, and — the front half of the per-row axis — that a new per-row ledger acquires a term at all. Three routes still compile: a new `RowBudget` variant answered with `0`, one answered with an EXISTING `RowBudgets` field (the shape a careless author actually writes, verified by mutant), and a ledger that reuses a variant or reports through some other error type. Routes 1 and 2 leave a lexical trace and a census trips on them (`tests/logql_row_budget_enumeration.rs`, variants counted against fields); route 3 leaves none. Closing it properly would mean making a per-row ledger unconstructable except through one sealed type that reads its ceiling out of this table — the shape the template module already uses for render output — which is a cross-cutting refactor of both ledgers and is not attempted here. Two source censuses cover those as tripwires — every production `caps.<field>` read (which is what catches a counter charged inline rather than through a gate function) and every charge-gate call's counter expression — and they are lexical, so they are tripwires and not proofs. The counters are deliberately NOT collapsed into one pot: sharing them would save ~0.8 GB (the same operational band) at the price of rejecting the high-cardinality `sum by (…)` shapes issue #236 exists to serve. The two RESULT budgets are summed rather than shown to be disjoint: `Plan::Streams` and `Plan::Metric` are mutually exclusive so no one query holds both, but proving that disjointness is a new claim and over-charging is the safe direction. Stated residuals, not covered by this figure: accumulated leaf RESULTS across a binary chain (#257/#285), post-aggregation grouping keys (#241), and process RSS under concurrency, which is `N ×` the above and is an operational sizing concern rather than a per-query bound.

**LogQL pipeline exact fetch-until-limit (M6-09, #90):** pipelines containing an in-engine dropping stage that cannot push down (a label filter, or a line filter after `line_format`) are served by keyset-cursor paging: the engine pages `reader.logql_pipeline_scan_factor × limit` rows at a time (default factor 10) through the pipeline until the true `limit` fills, the query window is exhausted, or the byte scan budget is spent. Responses fill exactly to `limit` (no under-return) and never over-return; the fast/non-dropping paths keep a single byte-identical `LIMIT` scan. The byte scan budget (`reader.logql_scan_budget_bytes`) is the hard cumulative scan ceiling and aborts first — a budget-truncated result returns the survivors so far and signals incompleteness via `data.stats.pulsus_partial` (configuration.md §6, api.md §2.1/§2.2).

**Read-path differentiators:** token/ngram skip indexes accelerate line filters (no full body scans within the selected streams); stream-selector-bounded scans otherwise; per-query scan budget with explicit "query too broad" errors instead of OOM.

**PromQL — M2 proof subset, evaluated with Prometheus-exact semantics** (counter resets, extrapolation, staleness markers, lookback delta, Kahan summation — validated by differential testing against Prometheus on exactly this subset): selectors with all matcher types; `offset`; `rate`, `irate`, `increase`, `delta`; `avg/min/max/sum/count_over_time`; aggregations `sum`, `avg`, `min`, `max`, `count`, `topk`, `bottomk` with `by`/`without`; vector–scalar and vector–vector arithmetic/comparison with `bool`, `on()`, `ignoring()`; `histogram_quantile`. Enough to power a typical dashboard and prove the hybrid engine.

**PromQL — parity (M6):**

- *Rate family:* `idelta`, `deriv`, `predict_linear`, `resets`, `changes`
- *Over-time:* `stddev/stdvar/last/present/quantile/mad_over_time`, `double_exponential_smoothing`
- *Aggregations:* `group`, `stddev`, `stdvar`, `quantile`, `count_values`, `limitk`, `limit_ratio`
- *Math & trig:* `abs`, `ceil`, `floor`, `round`, `sqrt`, `exp`, `ln`, `log2`, `log10`, `sgn`, `clamp{,_min,_max}`, full trig set, `deg`, `rad`, `pi`
- *Label & sort:* `label_replace`, `label_join`, `sort{,_desc}`, `sort_by_label{,_desc}`
- *Other:* `absent`, `absent_over_time`, `scalar`, `vector`, `time`, `timestamp`; `group_left()`/`group_right()` matching; set operators
- *Documented deviation (M6-03):* the date/time-field functions (`year`, `month`, `day_of_month`, `day_of_week`, `day_of_year`, `days_in_month`, `hour`, `minute`) map `NaN`/`±Inf`/out-of-`int64`-range input values to `NaN` — Go's `int64(float64)` conversion is platform-defined on exactly those inputs, so PulsusDB pins a total, documented behavior instead; finite in-range inputs truncate toward zero identically to Go
- *Modifiers:* `@` timestamp lands with M3
- *Subqueries* `metric[1h:5m]`, duration expressions, UTF-8 label names, and flag-gated experimental functions — all part of M6 full compliance
- *Accepted divergence — expression depth:* a parsed PromQL expression deeper than **250** levels is refused with `400 bad_data` naming the depth measured and the limit. Prometheus imposes no such bound and answers those queries; a Rust stack overflow aborts the process, so one deep request would otherwise kill every in-flight query on the node. Ledgered as `promql-expression-depth-cap` in [api.md §3.5](api.md), which also records what the cap does **not** cover.
- *Native histograms:* **M7** (committed, not aspirational) — histogram sample storage, OTLP exponential-histogram native ingestion, the histogram function set, and the upstream `native_histograms.test` corpus file passing

**Full compliance is the M6 bar, defined mechanically:** every function in the pinned Prometheus release's registry (89 at v3.13 — the function-only count: the 14 aggregation operators and the tracked language features are separate, separately-counted dimensions), the full operator/modifier matrix, and a 100% pass on the pinned upstream PromQL test corpus (~11.7k lines across 21 scenario files, fetched at test time and checksum-verified against a committed manifest) replayed against PulsusDB in CI. **What that replay executes is `parse` -> `plan` -> `evaluate`, and nothing below it:** the corpus driver resolves and windows series from a hermetic in-memory fetch stand-in (`crates/pulsus-promql/tests/promqltest/store.rs`, whose module header carries a machine-checked inventory of what it substitutes and which suite covers each stage instead), never a ClickHouse query — `pulsus-promql` has no dependency edge to `pulsus-read` at all, normal or dev. The fetch layer itself — series resolution on both the warm-cache and SQL-fallback paths, sample and histogram fetch, and selector-matcher semantics — is gated instead by the env-gated live suites `crates/pulsus-read/tests/live_metrics_engine.rs` and `crates/pulsus-read/tests/live_metrics_cache.rs`, which CI runs against a real ClickHouse in the `schema-it` job. The machine-checked coverage authority is `crates/pulsus-promql/tests/promqltest/coverage/function-coverage.json` (M6-01): every registry function, aggregation operator, and tracked language feature carries a CI-verified status there, and the drift test fails when the evaluator's real surface disagrees with it in either direction. PulsusDB never relies on ClickHouse's own (small-subset) PromQL support — evaluation is entirely in the engine, so language coverage is never constrained by what ClickHouse can express ([architecture.md §5.1](architecture.md)).

**TraceQL coverage (M4 + M7 structural):** span attribute selectors (`span.`, `resource.`, and the unscoped `.attr` form), intrinsics `name`, `duration`, `status`, `kind` (`service` is not an intrinsic — it is the `resource.service.name` attribute), comparison operators incl. regex, field-vs-field comparison (`{ .a = .b }`, issue #183), bare boolean statics (`{ true }`/`{ false }` — on the **metrics** routes too since issue #351, where `{ true }` is exactly the `{ }` match-all and `{ false }` its empty counterpart), static-vs-static comparisons folded to a constant at plan time (`{ "x" = "y" }`, issue #351), boolean-valued comparison operands (`{ .a = .b = .c }` — left-associative — and `{ !.a = !.b }`, issue #351: a non-boolean or absent operand is no match, while a present non-boolean under `!` fails the query as the reference does), multi-valued event/link comparison operands (`{ .a = event:name }`, issue #351 — any-match; see the intrinsics paragraph below), and unary field negation (`{ !(.a = 1) }`, `logic.not`), `&&`/`||` within and across spansets (`{...} && {...}`), aggregate filters (`count()`, `avg(duration)` etc.), `select()`, and the **complete** structural operator surface — `>` (child), `>>` (descendant), `<` (parent), `<<` (ancestor), `~` (sibling), each with its negated (`!>` …) and union (`&>` …) modifier (M7, issues #172/#183; RHS/negated/union result semantics, docs/api.md §4.2). Only `>=`/`<=` between spansets stay unsupported (not real Tempo operators).

**Colon-scoped and trace-level intrinsics (M7, issue #184):** the `span:`/`trace:` intrinsic namespace to Tempo v3.0.2 parity — `statusMessage`/`span:statusMessage` (the OTLP `Status.message`, stored on `trace_spans.status_message` since migration 35), `span:id`, `span:parentID`, `span:childCount`, `trace:id`, and the trace-level `traceDuration`/`trace:duration`, `rootName`/`trace:rootName`, `rootServiceName`/`trace:rootService` (bare legacy spellings included; `span:name`/`duration`/`status`/`kind` normalize onto their bare forms). Trace-level values are **full-trace-exact** — evaluated from per-batch trace-wide co-loads (window- and cap-independent, `pick_roots`-consistent root selection; docs/schemas.md §4.2), never from the truncated window view. Filtering only, with one exception: `select(span:id)` and `select(trace:id)` are **accepted and project nothing** (issue #351), which is the reference's own rule — its response builder skips both when filling a span's attribute list because each is already in the response envelope (`spanID`/`traceID`; `pkg/traceql/engine.go:322-331` @ v3.0.2). `select()` of the remaining colon-scoped/trace-level intrinsics, and numeric aggregation of `childCount`/`traceDuration`, stay unsupported. **Instrumentation scope (issue #192):** the `instrumentation.` attribute namespace (indexed under `scope='instrumentation'` in `trace_attrs_idx`) and the `instrumentation:name`/`instrumentation:version` intrinsics (the `scope_name`/`scope_version` physical columns on `trace_spans`, migrations 37/38) are supported, and `compare()` emits their real values. **Span events (issue #192 PR-B):** the `event.` attribute namespace (indexed under `scope='event'`) and the `event:name`/`event:timeSinceStart` intrinsics (indexed under the dedicated `scope='event:intrinsic'`, `timeSinceStart` as the event's ns offset from its span start in `val_num`) are supported — index-served like any attribute, with a hard namespace partition so a sender attribute cannot shadow an intrinsic. Compared against another **field** (`{ .a = event:name }`, issue #351) they are **multi-valued**: the span matches when **any** of its events satisfies the comparison, and `!=` matches only when **every** one does (so a span with no events satisfies it — the same absent-key rule the literal form follows). That is the reference's own designed multi-value rule and its pushdown behaviour; its field-vs-field path instead answers from the FIRST event only, which is a ratified divergence (`traceql-event-link-operand-any-match` in docs/benchmarks/traces-differential-ledger.md, with the evidence and the migration copying it would need). **Span links (issue #192 PR-C):** the `link.` attribute namespace (indexed under `scope='link'`) and the `link:spanID`/`link:traceID` intrinsics (indexed under the dedicated `scope='link:intrinsic'`, the referenced ids as lowercase hex in `val`) are supported the same way, with the same hard partition — including the multi-valued any-match rule above when compared against a field. With this the whole OTLP span-event / span-link / instrumentation-scope set is indexed and searchable: **TraceQL conformance carries no tracked interim constructs (interim == 0)** — the #185 closeout allowlist is empty and the strict gate enforces it. The `interim == 0` gate is **parse-level** — `crates/pulsus-traceql/tests/conformance/dispositions.json` says so in its own `comment` field ("'supported' is PARSE-level conformance"), and the differential suite beside it observes only the reference's HTTP status. Answer-level comparison against the reference lives in `pulsus-read`, in four suites of two different kinds. Three are two-system differentials that push the same OTLP spans into the pinned `grafana/tempo` v3.0.2 container and compare its live answers with ours: `compare_value_differential.rs` (the `compare()` per-value baseline/selection counts) and `traces_search_grouping_differential.rs` (`by()`/`coalesce()` grouped spanSet arrays, including wire typing) run **enforced** in CI's `schema-it` job, while `nestedset_value_differential.rs` (`nestedSetLeft`/`Right`/`Parent` numbering) is env-gated and **no workflow supplies its gate**. The aggregate `--workspace` run in the `ci` job does execute its binary — with the two `PULSUSDB_NESTEDSET_*` variables and a Tempo container absent it self-skips and CI reports it green, so no workflow ever observes its result. Run by hand against the pair it needs, it **fails today by design** on two of its three fixture classes — contrary sibling order and window clipping — which are the #185 closeout's open parity work, not a passing gate. The fourth, `traces_log2_reference.rs`, is **hermetic**: it replays a committed capture of the same reference rather than querying it live, and its `quantile_over_time` half is a characterisation oracle for a ledgered divergence (`2026-08-05-traceql-quantile-over-time-tdigest`), not a parity assertion.
